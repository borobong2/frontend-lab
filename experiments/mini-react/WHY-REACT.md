# React가 필요한 이유를 확인하기

이 문서는 첫 실험을 위한 질문 지도입니다. React 사용을 결론으로 정해 두기보다, 현재 화면에서 어떤 관리 비용을 줄여 주는지 확인합니다.

## 사용자 문제에서 시작

사용자는 상품을 찾고, 조건을 바꾸고, 상품별 메모를 남깁니다. 요청이나 이벤트가 성공하는 것만으로 충분하지 않습니다. 화면의 목록·개수·메모가 현재 조건과 일치해야 합니다.

프론트는 의도를 입력으로 받고 시스템 상태를 사용자가 이해할 수 있게 표현합니다. 이 예제에서 HTML은 의미와 기본 입력 동작, CSS는 배치, JS는 데이터와 DOM 연결을 담당합니다. 서버는 현재 없습니다. 나중에 실제 API를 붙이면 데이터 조회·권한 검증 같은 서버 책임과 UI의 표시 책임을 구분합니다.

## 직접 DOM을 다룰 때의 질문

1. 검색어를 바꾸면 목록 외에 무엇을 바꿔야 할까?
2. 필터와 검색을 결합하면 같은 갱신 코드를 재사용할 수 있을까?
3. 목록을 새로 만들면 메모와 입력 포커스는 어디에 남을까?
4. 같은 행 UI가 여러 화면에 쓰이면 구조와 동작을 어떻게 함께 재사용할까?
5. 새 조건이 생겼을 때 이벤트 처리마다 변경해야 할까?

순수 JS로도 해결할 수 있습니다. 해결 과정에서 직접 만든 규칙과 관리해야 하는 상태를 기록하세요.

## React가 제공하는 모델

- 컴포넌트로 UI를 나누고 props로 조합합니다.
- 상태를 기준으로 현재 UI가 어떤 모습이어야 하는지 표현합니다.
- 렌더링으로 다음 UI를 계산하고 커밋에서 DOM 변경을 적용합니다.
- 트리의 위치·타입·key를 바탕으로 상태의 정체성을 관리합니다.
- effect로 외부 시스템을 동기화하고 정리할 수 있습니다.

이 모델은 API 요청 경쟁, 접근성, 보안, 올바른 상태 설계를 자동으로 해결하지 않습니다. 정적 문서나 작은 상호작용에는 브라우저 기본 기능과 짧은 JS만으로 충분할 수 있습니다. 도입 판단에는 UI 복잡도·팀의 경험·운영 비용을 함께 봅니다.

## 실험에서 검증할 주장

| 가설 | 확인 방법 |
|---|---|
| 상태에서 UI를 계산하면 표시 불일치를 줄일 수 있다 | 원본 상태를 정하고 목록·개수를 함께 계산해 변경 지점 비교 |
| 매번 DOM을 교체하면 입력 경험이 달라진다 | DOM 참조·포커스·커서 위치를 교체 전후 관찰 |
| 목록의 위치와 항목의 정체성은 다르다 | 메모가 있는 항목의 순서를 바꾸고 어느 항목에 메모가 남는지 확인 |
| 컴포넌트마다 독립 메모리가 필요하다 | 같은 함수로 만든 두 카운터 중 하나만 변경 |

가상 DOM이 항상 더 빠르다는 결론은 내리지 않습니다. 성능을 주장하려면 같은 작업·환경에서 측정하고 비교 비용까지 포함해야 합니다.

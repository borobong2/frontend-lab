# 미니 React 단계별 실험 과제

각 단계는 구현 요구사항이며 아직 구현·학습 완료된 내용이 아닙니다. 먼저 예상하고 최소 기능만 만든 뒤 실패 조건을 검증하세요. 한 단계가 90분 안에 끝나야 하는 것은 아닙니다.

## 0 순수 JS의 갱신 책임

- 대상: 제공된 main.js와 검색 화면.
- 예측: 검색어·재고 필터·정렬 중 하나만 바뀌면 어떤 함수와 DOM이 바뀌는가?
- 실험: 결과 개수 갱신 한 줄을 잠시 제외하고 실제 목록과 개수가 다른 상황을 재현한 뒤 복구.
- 확인: 기본 5개, 키보드 2개, 재고 필터와 키보드 조합 1개.
- 설명: 원본 데이터·입력 상태·계산 값·DOM에 저장된 값을 구분.
- 변형: 품절 개수를 별도로 표시한다면 갱신 책임을 어디에 둘지 먼저 설명.

## 1 UI 설명 객체와 렌더러

- 인터페이스 제안: h(type, props, ...children), mount(element, container). 정답 구현은 제공하지 않음.
- 최소 지원: HTML 태그, 텍스트·숫자, 중첩 요소, className, 기본 클릭 이벤트. 지원하지 않는 props는 명시.
- 예측: h() 호출만으로 브라우저 DOM이 바뀌어야 하는가?
- 확인: 중첩 제목·버튼을 생성하고 클릭이 한 번 실행됨. 문자열 `<b>문자</b>`는 HTML이 아니라 텍스트로 보임.
- 주의: mount는 이번 단계에서 최초 생성만 담당. 갱신 정책을 몰래 추가하지 않음.
- 변형: 자식이 0개·1개·여러 개인 경우. null·배열 지원은 다음 필요가 생기면 추가.
- 설명: UI 설명 객체와 DOM 객체의 수명·역할 차이.

## 2 함수 컴포넌트와 조합

- 요구: type이 함수이면 props를 전달해 반환한 UI 설명을 렌더링. children 전달 계약을 직접 정함.
- 확인: ProductRow 함수 두 개에 서로 다른 상품을 전달하고 중첩 컴포넌트도 표시.
- 실패: 함수 반환값을 문자열로 표시하거나 props를 공유·변경하는 경우를 구분.
- 변형: 부모의 props 변경에 따라 다른 내용을 계산.
- 설명: props는 입력이고, 아직 인스턴스별 상태는 구현하지 않았음을 구분.

## 3 상태 저장과 다시 그리기

- 범위: 단일 루트 상태와 갱신 함수. 아직 useState 이름을 붙일 필요 없음.
- 요구: 상태 변경 → UI 계산 → 화면 반영 흐름을 명시. 초기 버전은 전체 교체 허용.
- 확인: 카운터 버튼으로 값 변경. 검색 결과와 개수는 같은 원본 상태에서 계산.
- 실험: 입력 중 전체 루트를 교체할 때 activeElement·커서·입력값 관찰.
- 설명: 일반 변수를 바꾸는 것, 값을 다음 호출까지 보존하는 것, 갱신을 요청하는 것은 다른 책임.
- 변형: 이전 값에 기반한 변경을 두 번 적용할 때의 기대 결과를 적음. batching은 아직 구현하지 않음.

## 4 DOM 재사용과 patch

- 요구: 같은 태그의 기존 노드를 재사용하고 텍스트·속성·이벤트의 추가/변경/제거 처리. 다른 타입은 교체.
- 범위: 먼저 순서가 고정된 자식만 지원. key는 다음 단계.
- 확인: 다른 상태를 바꿔도 입력 DOM 참조가 같음. 이벤트 핸들러 변경 후 이전 핸들러가 함께 실행되지 않음.
- 경계: value와 checked는 DOM property와 attribute를 구분. 없는 속성·이벤트 제거도 확인.
- 변형: 자식 추가·삭제, 문자열에서 요소로 변경.
- 설명: 컴포넌트 재계산과 실제 DOM 변경 횟수가 같지 않은 이유.

## 5 key와 상태의 정체성

- 요구: 같은 부모 아래 type·key로 이전 항목을 찾고 재사용·이동·삭제. 중복 key는 지원하지 않음을 명시하거나 진단.
- 확인: 세 행 각각에 메모를 쓰고 앞에 삽입·역순 정렬·중간 삭제. 메모가 해당 항목을 따라가는지 확인.
- 주의: 제공된 출발점은 ID별 Map으로 메모를 복원하므로 이 검증을 가릴 수 있음. 별도 예제에서는 외부 Map 복원을 사용하지 않고 DOM 입력값으로 노드 정체성을 먼저 확인.
- 단계 6 이후: 같은 시나리오를 행 내부 useState로 재검사.
- 비교: 위치 기준 대응과 key 기준 대응. 다른 부모의 같은 key를 동일 인스턴스로 취급하지 않음.
- 수명: key를 바꾸거나 항목을 제거한 뒤 다시 넣으면 로컬 상태가 초기화되는 모델. 외부 저장소의 메모 보존과 구분.

## 6 컴포넌트별 useState

- 요구: 인스턴스마다 상태 슬롯과 훅 커서를 유지. 렌더 시작 때 커서는 초기화하되 슬롯 값은 보존.
- 확인: 같은 Counter 두 개 중 하나만 증가. 한 컴포넌트의 여러 상태가 각각 유지. 두 행의 정렬 후에도 상태가 올바른 항목에 남음.
- 실패: 조건에 따라 앞쪽 훅 호출을 생략해 뒤쪽 상태가 어긋나는 상황을 작은 예제로 관찰.
- 경계: 제거된 인스턴스 정리. 같은 타입이더라도 위치/key가 바뀌면 상태 수명을 다시 판단.
- 설명: 전역 배열 하나의 한계. 실제 React의 내부 자료구조와 이 교육용 슬롯 모델을 동일시하지 않음.
- 선택: 함수형 updater와 갱신 큐. 이 경우 고정 값 갱신과 이전 상태 기반 갱신을 비교.

## 7 외부 동기화와 cleanup

- 최소 예제: 타이머 또는 window 이벤트 구독 중 하나.
- 요구: DOM 반영 후 실행할 effect를 모으고 의존성 변경 전 이전 cleanup, 제거 시 cleanup. 의존성 비교 규칙 명시.
- 확인: 의존성이 같으면 재구독하지 않음. 바뀌면 이전 작업 종료 후 새 작업 시작. 제거 뒤 타이머·구독이 남지 않음.
- 경계: 의존성 생략·빈 배열·값 배열을 구분. 정확한 paint 시점·React 스케줄링은 재현하지 않음.
- 변형: 검색 응답 역전 예제로 오래된 결과의 반영 권한 판단. AbortController가 모든 Promise를 취소한다고 가정하지 않음.
- 설명: 이벤트 처리로 충분한 작업과 외부 시스템 동기화를 구분.

## 단계별 검증 기록

각 단계에서 하나씩 남깁니다: 실행 전 예상, 재현 순서, 실제 관찰, 수정 이유, 우리 구현의 한계, 실제 React와 비교한 버전·결과.

브라우저 수동 확인으로 시작하고, 반복하거나 깨지기 쉬운 행동은 작은 회귀 테스트로 남깁니다. 테스트 도구를 먼저 크게 구축하지 않습니다. 공식 문서 링크는 [실험 안내](README.md#공식-근거와-비교)를 사용하세요.

## 멈춰도 되는 지점

단계 0–3: 선언적 UI와 갱신의 필요성 설명 가능.
단계 4–5: DOM 재사용과 key를 실제 실패로 설명 가능.
단계 6–7: 훅 상태와 외부 동기화의 수명 설명 가능.

각 지점에서 실제 React 코드에 배운 원리를 적용해 보고 다음 단계의 필요성을 판단합니다. 모든 단계 완주를 이직 지원 조건으로 두지 않습니다.
